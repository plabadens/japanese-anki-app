## Implemented API contract

New production source: `app/src/main/java/dev/pierre/japaneseanki/VerifiedFirstRunResources.kt`.

- `FirstRunResource` and `FirstRunResourceManifest` defensively copy their collections and reject malformed ids/versions/targets, duplicate ids/targets, non-HTTPS or query-bearing manifest URLs, malformed SHA-256, invalid byte limits, and unsafe archive paths.
- `VerifiedFirstRunResourceInstaller` accepts an injected `ResourceTransport`; production uses HTTPS, bounded redirects, connect/read timeouts, and refuses HTTPS downgrade. `ResourceCancellation` and a thread-interruption check are sampled while streaming.
- Exact expected byte count is a hard transfer bound. `Content-Length`, when present, must match. The digest is calculated in the bounded streaming pass; the payload is not activated unless byte count and build-pinned SHA-256 match.
- ZIP resources are checked before activation for valid central-directory structure/CRC, exact expected entry names and sizes, duplicate/unexpected/missing entries, and traversal paths. The core validates archives but does not extract them; extraction remains the caller's separately audited responsibility.
- Verified bytes are fsynced to a same-directory `.part` and moved with `ATOMIC_MOVE`. There is no non-atomic fallback. Failed/cancelled attempts remove the partial file; a process-killed `.part` is discarded on retry. Existing active version files remain untouched when a new transfer fails.
- Results distinguish `DOWNLOADED`, `REUSED`, and `ADOPTED_LEGACY`; a legacy validator can fully validate an existing file/directory and return it directly without copying or downloading. The validator must check the real schema/content, not mere existence.
- Typed failure classes distinguish HTTP status, transfer, integrity, archive, storage preflight, activation, and cancellation. Progress carries the resource id, phase, exact byte count, and total so onboarding can render one progress item per resource.
- The core deliberately does not auto-retry or resume partial HTTP ranges. Explicit retry starts from byte zero and is deterministic; no partial is ever mistaken for a valid installation.

No production resource entries have been created: hosting is unresolved and a trusted manifest must not contain a made-up URL/hash. The code is not wired into app runtime lookups. Later onboarding integration owns orchestration and must pass the `ReadyResource.location` to resource-specific validation/activation adapters.

## Delivery recommendation and unresolved decisions

1. Host immutable, versioned generated artifacts as GitHub Release assets over HTTPS, with durable asset URLs, exact lengths and build-pinned SHA-256 values. GitHub's current release documentation allows each asset to be under 2 GiB and states no total-release-size or bandwidth-usage limit; the current UniDic runtime archive is 446,602,958 bytes and fits the per-asset bound. Source: https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases. Use ordinary release-asset URLs in the manifest; the transport follows a bounded HTTPS redirect (including a temporary signed CDN query) without logging it. No upload/release was attempted or authorized.
2. Keep executable MeCab JNI/native libraries in the APK. Deliver data-only resources at onboarding. The onboarding manifest should pin the exact artifact SHA-256 and exact compressed length in the APK; a new artifact version is a code-reviewed manifest change. Keep old versioned resources until new validation/activation succeeds.
3. Decide whether the NHK index joins first-run provisioning. Its current first audio request causes a runtime dataset download and lacks a build hash; moving that JSON to onboarding would meet the resource gate, but does not settle recording rights or make remote recordings available offline.
4. Resolve AJT pitch data licensing and monthly JMdict update ownership before creating the final manifest or publishing generated resources.
5. OCR is the hard tradeoff. If the no-model-in-APK rule is strict and an exact app-pinned hash is required, the Play-Services-managed ML Kit coordinate is not a fit. Either approve Google-managed model integrity as an explicit exception (no app SHA check), keep the current bundled ML Kit model and explicitly exempt its small build dependency, or approve a self-hosted model/backend with a verifiable model file/hash. The existing Tesseract provenance note is a lead only; its dependency, model URLs, hashes, license and output parity must be reverified before migrating. No OCR migration was made.
6. Onboarding must include individual progress, cancel/retry, low-storage recovery, offline reuse after successful provisioning, and explicit legacy probes. Default to Wi-Fi; if mobile data is selected, show the total download size and require explicit confirmation first. Do not mark onboarding complete until the shared Google API key and a valid voice selection are present. It must not remove bundled resources until the approved manifest and migration path are exercised on fresh and upgraded installs.
