# Final mockup and specification review

Reviewed the 33 portrait mockups, their HTML/CSS and walkthrough, dark-theme and short-landscape renders, `SPEC.md`, and the pinned AnkiDroid v2.24.1 source. The mockups are **static design references**, not evidence of a working Compose implementation. The existing app implementation predates several of these requirements.

## Assessment

The card-and-sheets structure, restrained neutral palette, pitch-focused color, and strong separation between capture, target selection, and send are coherent. The single review hub is an efficient use of a phone screen; Settings stays out of repeated note creation. The earlier art had three material quality problems: unreadable dark secondary text, incomplete card backdrops, and small/ambiguous controls. These were addressed in the design artifacts. A fresh review additionally caught low-contrast disabled Next and Sending states; both now use theme-safe neutral foreground/background pairs instead of opacity or muted-on-rule. Native TalkBack, 200% font scaling, insets, keyboard behavior, scrolling, and 48dp targets **still require Android tests**. The fixed portrait PNG alone cannot prove them.

## Clarifications applied

- **User decisions:** automatic, optional readings everywhere (no manual kana/omission controls); preserve the draft after unexpected errors; on a dictionary miss preserve text and permit edit/reselection instead of forced restart. `SPEC.md` §§4.4, 4.10, 5.4, 9.2, 14, 17 and screens 11–12 reflect these decisions.
- Clarified target-span and dictionary-entry reselection, Notes/definition editing completion, tag add/remove, back navigation, field-state retry, protected manual translations, and frozen sending/uncertain-outcome flows. A failed/incomplete optional item can be retried; valid completed audio/translation is not manually regenerated. These are *specification* behaviors, not newly implemented application features.
- Separated the Android TTS offline-audio fallback from the independent bundled translation model. Azure Speech and Translator may share a **multi-service resource key**, but must each be authorized/tested; merely having an Azure account does not guarantee both. Settings screens 30–31 and §4.9 now say so.
- Brought the pitch/reading examples into agreement: `上手` has ruby in the sentence and vocabulary, the compact diagram identifies the vocabulary reading rather than assuming inflected sentence ruby matches it, pitch selection uses a neutral check/border as well as color, and the odaka reference adds a word-boundary tail rather than relying solely on hue. Long diagrams scroll; absent/unverified recording-pitch metadata is explained without claiming a match.
- Improved the mockups' baseline contrast and control sizing, made modal edit sheets retain the complete review hub, made screens scrollable at reduced viewport height, added Settings back controls and a valid-note-type cue, removed meta copy from user-facing screens, and kept the pitch popover inline without obscuring Send. Source HTML now declares viewport metadata and the render script creates a private Chromium profile.
- Scoped duplicate navigation to **AnkiDroid’s browser filtered by note ID**, not the scheduler. In the pinned source, `AnkiDroid/src/main/AndroidManifest.xml` exports the browser at `anki://x-callback-url/browser`, `browser/CardBrowserLaunchOptions.kt` reads a `search` parameter, and the search UI accepts `nid:<id>`. This is stronger source evidence than an unknown route, but still **not an on-device integration test**.

## Feasibility and release gates

| Area | Current evidence | Still needed before claiming release readiness |
|---|---|---|
| AnkiDroid duplicate/export | API and local gateway support model/deck inspection and candidate queries; `bulkInsert` returns a count rather than an ID; query-then-insert is not atomic against other writers. | Pin/test the installed release: trailing empty fields, card deck assignment, first-field/helper limitations, interrupted insertion and reconciliation, concurrent external writes, browser deep link. No promise of exactly-once insertion. |
| Japanese OCR | [ML Kit’s Android Japanese text recognition docs](https://developers.google.com/ml-kit/vision/text-recognition/v2/android) offer a **bundled** Japanese model in addition to the unbundled Play Services option. This is a candidate, not a chosen dependency. | Verify offline first launch, privacy/data-collection terms against §11, package/API support, actual photo quality, and build reproducibility. Alternative engines may be compared. |
| Local ja→en translation | [OPUS-MT ja→en](https://huggingface.co/Helsinki-NLP/opus-mt-ja-en) is an Apache-2.0 model-card candidate, **not** an Android runtime or validated translator. | Choose/pin a runtime and tokenizer, licenses for *all* artifacts, both ABI support, memory/latency/APK size, real short mined-sentence quality, fully offline cold start. TTS cannot translate. |
| AVIF | A supported encoder/backend has not been selected. Android image decoding or an `.avif` sample does not prove encoding support. | Pin encoder, verify both ABIs, metadata stripping, legible small text, and display in installed AnkiDroid. |
| Audio | Word-recording rights and Android offline file-synthesis support remain open; no source guarantees a matching accent pattern. | Prove recording authorization; audition voice/provider, validate offline engine availability and audio formats, represent unverifiable pitch honestly. |
| Reproducible build | SDK/API 35–37 and the Nix build are configured; implementation status reports the Gradle artifact lock and independent rebuild check pending. | Run clean locked builds twice and compare unsigned APKs; test target Android versions and both ABIs. |

[Azure Translator authentication](https://learn.microsoft.com/en-us/azure/ai-services/translator/text-translation/reference/authentication) distinguishes regional/global/multi-service resources; its headers and region must be validated separately from Speech. See `SPEC.md` §15 for the authoritative release gates. None of the candidates above is silently approved for shipping.

## Evidence and residual UI limitations

- `./mockup/render.sh` regenerated all **33 PNGs**. Core screen structural and PNG-dimension checks, `bash -n mockup/render.sh`, and `git diff --check` passed. Dark theme and short-landscape screens were rendered to `/tmp` for review; the card and sheets scroll rather than depend on a fixed 412px layout.
- Static mockups have no real keyboard, selection handles, hit-area hit testing, dynamic TalkBack semantics, or live font scaling. Compose must implement the `SPEC.md` contracts; screenshots must not be mistaken for accessibility acceptance. In particular, 200% text and a keyboard can push controls off a short screen; scrolling and focus management must be exercised on Android.
- The original 16px card icons are now shown within 48px reserved slots; screen CSS visual spacing is a design indication. The native app must give actual separate 48dp tappable regions to each play/edit/explainer control and sentence token, with accessible names and selected/disabled state.
- **Trade-off accepted by user:** if automatic readings are wrong or absent, there is no direct kana correction; users may change source text/entry/target or send without that furigana. Do not quietly reintroduce a blocking reading step.
